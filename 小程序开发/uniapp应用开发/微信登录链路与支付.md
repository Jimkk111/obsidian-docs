# 微信登录链路与支付

## 登录：uni.login → code → 后端换自定义登录态

```js
// 封装成 Promise（uni.login 本身是回调风格）
export function loginSync() {
  return new Promise((resolve, reject) => {
    uni.login({
      provider: 'weixin',
      success: (res) => (res.errMsg === 'login:ok' ? resolve(res.code) : reject(res)),
      fail: reject,
    })
  })
}

// 完整登录流
async function doLogin() {
  const jsCode = await loginSync()
  // code 传给自家后端，后端调 auth.code2Session 换 openid + session_key，
  // 生成自定义登录态（如 sessionId/token）返回
  const res = await userLogin({ phone: jsCode })
  if (res.code === 1) {
    useUserStore().setSession(res.data.sessionId)  // Pinia + storage 双写
  }
}
```

时序要点（面试必考）：

1. `uni.login` **静默**完成（无用户弹窗），拿到 5 分钟有效、一次性的 `code`。
2. `code → openid` 的交换**只能在服务端**做（要 appsecret），openid 与 session_key 永不落前端。
3. 前端持有的是后端发的**自定义登录态**，此后每个请求携带（header token 或 Cookie JSESSIONID）。
4. 登录失效：请求层统一拦 401/失效码 → 清 Pinia+storage → reLaunch 首页重新静默登录。

### 获取头像昵称（2022 后的现行方案）

`uni.getUserProfile` / `wx.getUserProfile` 已废弃，只会返回匿名数据（灰色头像 + "微信用户"）。现行**头像昵称填写能力**：

```html
<template>
  <button open-type="chooseAvatar" @chooseavatar="onChooseAvatar">
    <image :src="avatarUrl" />
  </button>
  <input type="nickname" v-model="nickname" placeholder="请输入昵称" />
</template>

<script setup>
function onChooseAvatar(e) {
  avatarUrl.value = e.detail.avatarUrl   // 微信推荐头像或用户相册选择
}
// input type="nickname"：键盘上方出现"使用微信昵称"快捷项
</script>
```

要点：用户**主动确认**头像昵称，前端拿到的是临时头像 URL，通常需上传到自家服务器/OSS；相比旧方案少了一次强制授权弹窗，合规且体验更轻。

### 手机号快捷登录（可选增强）

```html
<button open-type="getPhoneNumber" @getphonenumber="onGetPhone">
```

- 回调给 `code`，**后端**调 phonenumber.getUserPhoneNumber 换真实手机号。
- 需要**企业主体认证**的小程序，个人开发者拿不到——学习项目里做不了的原因先说清。

### 授权与设置

- `uni.authorize({ scope })`：预授权（相册、位置等），用户拒绝后引导 `uni.openSetting`。
- 用户信息 scope 的旧授权弹窗体系已随 getUserProfile 废弃，不要再写。

## 支付：uni.requestPayment

```js
// 参数全部来自自家后端（后端统一下单后签名返回）
uni.requestPayment({
  provider: 'wxpay',
  timeStamp: '',       // 时间戳（字符串）
  nonceStr: '',        // 随机串
  package: 'prepay_id=wx20170xxx',   // 统一下单返回的 prepay_id
  signType: 'RSA',
  paySign: '',         // 服务端签名
  success: () => { /* 体验层提示；真实结果以服务端回调为准 */ },
  fail: () => {},
})
```

完整链路与责任划分（面试重点）：

```
前端：提交订单 → 后端统一下单 → 拿回支付五元组 → uni.requestPayment 唤起收银台
后端：调微信 JSAPI 下单拿 prepay_id → 二次签名 → 接收微信支付回调 → 幂等处理订单状态
```

- **签名只出现在服务端**（涉及商户密钥）；前端 success 回调不可作为支付成功依据（网络丢单场景），必须以后端收到微信回调为准。
- 主体资质：真实支付需企业主体 + 微信商户号；**个人主体学习项目无法发起支付**，通常以后端模拟支付接口替代（这本身就是一句可以主动讲清的工程认知）。
- App 端支付还需在 manifest.json 勾选支付模块并配置各平台参数，小程序端用 mp-weixin.appid 对应的商户号。

## 多端差异速记

| 能力 | 微信小程序 | App | H5 |
|---|---|---|---|
| uni.login | wx.login → code | 各渠道 SDK（微信开放平台） | 通常自建账号/扫码 |
| 头像昵称填写 | 支持（基础库 2.21.2+） | 不支持 | 不支持 |
| getPhoneNumber | 企业认证可用 | 同左 | 不适用 |
| requestPayment | 微信支付 | 微信/支付宝 SDK | 通常跳转/二维码方案 |

同一套业务代码里用条件编译分流登录支付逻辑是 uni-app 项目的常态。

## 经验提示

- 登录竞态：首页 onShow 判断登录态后发请求，与静默登录并行会打到未登录接口——先 `await doLogin()` 再 `init()`，或请求层排队等 sessionId 就绪。
- 登录态存储三件套：Pinia（内存态）+ `uni.setStorageSync`（持久化）+ 请求头注入（使用态），三者同步更新收敛到 store 的 action 里，页面永远不直接操作 storage。
