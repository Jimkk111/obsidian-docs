# 事务（TCL）

事务（Transaction）是把一组 SQL 操作当作**不可分割的工作单元**来执行的控制机制，对应 TCL（Transaction Control Language，官方手册 13.3 Transactional and Locking Statements）。事务仅在使用事务型存储引擎（InnoDB）的表上有效。

## 一、四大特性（ACID）

| 特性 | 含义 |
| ---- | ---- |
| 原子性 Atomicity | 事务中的一组操作要么全部成功，要么全部失败回滚，不存在中间态 |
| 一致性 Consistency | 事务前后数据完整性不被破坏（如转账总额不变），是最终目的 |
| 隔离性 Isolation | 并发事务之间相互隔离，一个事务的中间状态对其他事务不可见 |
| 持久性 Durability | 事务一旦提交，对数据的修改永久保存，即使系统宕机也不丢失 |

InnoDB 的实现：原子性靠回滚日志 undo log，持久性靠重做日志 redo log，隔离性靠[[web后端开发/数据库/MySql/锁|锁]] + [[web后端开发/数据库/MySql/MVCC|MVCC]]。

## 二、基本操作

```sql
-- 查看提交方式（MySQL 默认 autocommit = 1）
SELECT @@autocommit;

-- 方式一：关闭自动提交，后续语句均需手动提交（仅当前会话有效）
SET autocommit = 0;

-- 方式二：显式开启事务（推荐）
START TRANSACTION;    -- 或 BEGIN;

UPDATE account SET money = money - 500 WHERE name = '张三';
UPDATE account SET money = money + 500 WHERE name = '李四';

COMMIT;               -- 提交：全部生效
ROLLBACK;             -- 回滚：全部撤销，回到事务开始前
```

### 保存点 SAVEPOINT

```sql
SAVEPOINT sp1;                    -- 设置保存点
DELETE FROM emp WHERE id = 3;
ROLLBACK TO sp1;                  -- 回滚到保存点（保存点之前的操作仍保留在事务内）
RELEASE SAVEPOINT sp1;            -- 删除保存点
```

## 三、隐式提交

某些语句执行时**会自动提交当前事务**（官方 13.3.3），事务中要避免混入：DDL 语句（CREATE / ALTER / DROP 等）、隐式使用库的语句（USE db）、多数管理语句（CREATE USER / GRANT 等）、`SET autocommit = 1` 等。这也是 **DDL 无法回滚** 的原因。

## 四、并发事务问题

多个事务并发操作同一数据时会产生：

| 问题 | 说明 |
| ---- | ---- |
| 脏读 Dirty Read | 一个事务读到了另一个**未提交**事务修改过的数据 |
| 不可重复读 Non-repeatable Read | 同一事务内两次读**同一行**，结果不同（别的事务提交了 UPDATE） |
| 幻读 Phantom Read | 同一事务内两次按相同条件查询，**记录数**不同（别的事务提交了 INSERT/DELETE） |

## 五、隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| ---- | ---- | ---- | ---- |
| READ UNCOMMITTED（读未提交） | 有 | 有 | 有 |
| READ COMMITTED（读已提交） | 无 | 有 | 有 |
| REPEATABLE READ（可重复读，**InnoDB 默认**） | 无 | 无 | — |
| SERIALIZABLE（串行化） | 无 | 无 | 无 |

- 隔离级别从上到下越来越安全、并发性能越差。
- InnoDB 在 RR 级别下通过 **MVCC** 让普通 SELECT（快照读）看不到其他事务后插入的行，通过**next-key lock** **（记录锁 + 间隙锁）** **阻止别的事务在锁定读范围内插入，基本解决了幻读；快照读与锁定读混用时仍可能出现幻读**。

```sql
-- 查看隔离级别（8.0 变量名是 transaction_isolation）
SELECT @@transaction_isolation;

-- 设置（GLOBAL 对新会话生效，SESSION 对当前会话生效）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

## 六、锁定读

在事务中可以对查询的行显式加锁：

```sql
SELECT * FROM account WHERE id = 1 FOR UPDATE;   -- 排他锁：别的事务不能读(锁)写这行
SELECT * FROM account WHERE id = 1 FOR SHARE;    -- 共享锁：别的事务可共享读，不能写
```

典型用法：先 `FOR UPDATE` 查余额再扣减，避免并发下的超扣。

### 2026-09-11 自动提交与出错回滚的细节

#### 1. 不手动 START TRANSACTION，一条 SQL 就是一个事务吗？

是。默认 `autocommit = 1` 时，每条 DML 语句会被隐式包成一个迷你事务：**执行成功立即自动提交，语句执行出错则自动回滚该语句**。一条 UPDATE 改 1000 行也仍然是原子的（要么全生效要么全撤销）。前提是 InnoDB 这类事务型引擎，MyISAM 根本不支持事务。三种模式对比：

```sql
-- 模式一：默认 autocommit = 1，一条语句一个事务，执行完立即自动提交
UPDATE account SET money = money - 500 WHERE name = '张三';

-- 模式二：显式开启事务（推荐）
START TRANSACTION;
-- ...多条语句
COMMIT;

-- 模式三：SET autocommit = 0 后所有语句都不再自动提交，必须手动 COMMIT
SET autocommit = 0;
-- 容易忘记提交导致长事务（锁长期持有、undo log 膨胀），生产慎用
```

#### 2. 事务执行出错会自动回滚吗？

不一定，**取决于错误类型**。"语句报错 = 整个事务自动回滚"是常见误解：

| 场景 | 行为 |
| ---- | ---- |
| 语句级错误（唯一键冲突、外键失败、溢出等） | 只回滚**该语句**，事务不结束，之前的修改仍有效，甚至可以继续 COMMIT |
| 死锁 Deadlock | InnoDB 自动回滚牺牲品事务（通常改的行数较少的那个）的**整个事务**，报 1213 错误 |
| 锁等待超时 | 默认 `innodb_rollback_on_timeout = OFF` 只回滚当前语句；设为 ON 回滚整个事务 |
| 客户端断连 / kill 连接 | 服务端自动回滚该连接上未提交的事务 |
| MySQL 宕机后重启 | 崩溃恢复阶段用 undo log 回滚所有未提交事务（ACID 原子性的体现） |
| 应用层异常（两条 SQL 之间 Java 代码抛异常） | 数据库不知情，事务照常挂着，必须由客户端自己发 ROLLBACK |

关键结论：MySQL 只对死锁、断连、宕机这类"事务无法继续"的情况自动回滚整个事务；普通语句报错只回滚那条语句，**整个事务回不回滚由客户端决定**——这正是 Spring `@Transactional` 捕获异常后主动发 ROLLBACK 的原因（回滚是客户端发起的，不是数据库自动做的）。

```sql
-- 语句级错误示例：报错的语句回滚，但第一条 UPDATE 仍有效
START TRANSACTION;
UPDATE account SET money = money - 500 WHERE name = '张三';  -- 成功
UPDATE account SET money = money + 500 WHERE name = '李四';  -- 报错（如约束冲突）
-- 事务没有回滚！第一条的修改还在，COMMIT 是合法的
```

#### 3. ROLLBACK 一定是回滚整个事务吗？

- 裸 `ROLLBACK`：回滚当前事务的**全部**未提交修改并结束事务（锁释放）。
- `ROLLBACK TO SAVEPOINT`：只部分回滚，事务继续开着（见上文"保存点"）。
- DDL 等隐式提交过的部分谁也回滚不了（见上文"三、隐式提交"）。
- 回滚是 InnoDB 用 undo log 逐条反做的，大事务（几十万行）的 ROLLBACK 本身可能耗时很久——避免大事务的又一原因。

### 2026-09-11 事务底层机制：COMMIT、存储文件与三大日志

#### 1. 隔离级别的本质

隔离级别描述的是**多个事务并发时，一个事务能"看到"其他事务未完成的中间状态到什么程度**，是"数据安全性 ↔ 并发性能"的权衡档位。理想隔离是串行执行（绝对安全但并发性能极差），放松限制跑得快但会出读异常——每升一档多防一种异常（脏读→不可重复读→幻读），代价是并发性能下降。

一个关键认知：**隔离级别决定的不是"未提交的修改存不存在"，而是"读的时候允不允许看最新版"**（见下一条）。

#### 2. 读未提交为什么能读到未提交的数据

"没提交" ≠ "改动看不见"。事务 A 执行 UPDATE 的那一刻：旧值拷贝进 undo log，**数据页（buffer pool）里的当前行当场改成新值**——新值从这一刻起就物理存在，提交与否只决定它能不能留下。

高隔离级别读不到，是**读的一侧加了过滤**：SELECT 时生成 ReadView，发现该行最新版本的修改者（`DB_TRX_ID`）未提交，就顺着 `DB_ROLL_PTR` 到 undo log 版本链里取旧版本返回（规则详见 [[web后端开发/数据库/MySql/MVCC|MVCC]]）。**READ UNCOMMITTED 只是不建快照、不做版本检查，直接读数据页里的最新版本**——这就是脏读的机制本质。

#### 3. COMMIT 到底做了什么

COMMIT **不是把数据写盘**（修改早已在 buffer pool 里，脏页通常此时还没落盘）。它做四件事：

1. **持久化 redo log**：把记录物理修改的 redo log 刷盘并 fsync（默认 `innodb_flush_log_at_trx_commit = 1`）——持久性 D 的实现，之后宕机也能靠它重放恢复；
2. **释放锁**（行锁、间隙锁）；
3. **修改对其他事务可见**（ReadView 检查发现已提交）；
4. **undo log 交给后台 purge 线程异步清理**（不立即删，见第 7 条）。

这就是 **WAL（Write-Ahead Logging，先写日志后写数据）**：redo log 顺序写、快，先行落盘保平安；数据页随机写、慢，由后台线程慢慢刷。

#### 4. 数据都存在哪（重点）

**内存（InnoDB 内）：**

| 位置 | 存什么 |
| ---- | ---- |
| Buffer Pool | 数据页/索引页（16KB 一页）的缓存，**读写都先在这里**；改过未刷盘的页叫**脏页** |
| Log Buffer | redo log 的内存缓冲，事务执行中先写这里，COMMIT 时刷盘 |

**磁盘（文件）：**

| 文件 | 存什么 |
| ---- | ---- |
| `.ibd` 表空间文件 | 数据和索引真正的家（B+ 树页），脏页最终刷到这里 |
| redo log（`ib_logfile0/1`） | 重做日志：记录**物理修改**（第几页改成啥），循环写，用于**宕机恢复已提交**的数据 |
| undo 表空间（`undo_001` 等） | 回滚日志：记录**逻辑反操作** + 行的旧版本，用于**回滚未提交**事务 + MVCC 版本链 |
| binlog（Server 层） | **逻辑日志**（类似 SQL），追加写，用于主从复制、误操作恢复 |
| Doublewrite Buffer | 防止刷页写一半断电导致"页断裂"（半页写入） |

一次 UPDATE + COMMIT 的完整旅程：

```text
UPDATE account SET balance = 200 WHERE id = 1;
 │
 ├─ ① 旧值 100 写入 undo log（供回滚 / MVCC）
 ├─ ② buffer pool 中该数据页改成 200 → 成为脏页（暂不落盘）
 └─ ③ "某页某处改成了 200" 记入 redo log buffer

COMMIT;
 │
 ├─ ④ redo log buffer 刷盘 + fsync        ← 唯一必须同步落盘的动作（持久性）
 ├─ ⑤ 释放行锁、间隙锁
 ├─ ⑥ 修改对其他事务可见
 └─ ⑦（此后某时刻）后台线程把脏页刷回 .ibd 文件 ← 异步，不阻塞 commit
```

宕机恢复 = **用 redo log 重放所有已提交事务 + 用 undo log 回滚所有未提交事务**，ACID 的 A 和 D 由此落地。

#### 5. redo log 细节

**解决什么问题**：每次修改就刷数据页不可行（改几字节要随机写 16KB，写放大 + 随机 IO 慢）；不刷盘断电又丢。redo log 是折中：每次只在日志末尾**顺序追加**一条几十字节的物理记录（"3 号页偏移 128 处改为 200"），COMMIT 时只需 fsync 这点日志；数据页异步慢慢刷。类比：数据页是**余额**，redo log 是**银行流水**——流水小而快，余额可以从流水重放出来（"redo" = 重做）。

**循环写**：文件大小固定，写满一圈从头覆盖，像环形跑道：

```text
┌──────────────────────────────────────┐
│ #####→  ..............   ←#####      │
│  write pos              checkpoint   │
└──────────────────────────────────────┘
write pos  ：日志写到了哪
checkpoint ：它之前的脏页已刷回 .ibd，对应日志可覆盖
write pos 追上 checkpoint 时，InnoDB 被迫停下强制刷脏页 → 大事务卡顿的常见原因
```

**刷盘参数** `innodb_flush_log_at_trx_commit`：

| 取值 | 行为 | 代价 |
| ---- | ---- | ---- |
| 1（默认） | 每次 COMMIT 刷盘 + fsync | 最安全，已提交数据绝不丢 |
| 2 | 每次 COMMIT 写到 OS 缓存，每秒 fsync | 快；OS 崩溃丢 1 秒 |
| 0 | 每秒刷一次 | 最快；MySQL 挂了丢 1 秒 |

#### 6. fsync 是什么

fsync 是操作系统系统调用：**强制把该文件在 OS 页缓存里的数据真正写到物理磁盘介质，并等磁盘确认写完才返回**。写文件其实要过四层，`write()` 返回只代表数据进了 OS 页缓存（内存）：

```text
MySQL 进程内存 ─write()→ OS 页缓存 ─fsync→ 磁盘控制器缓存 ─→ 盘片/闪存
（应用崩了不丢）        （OS 崩了丢）        （断电才可靠，须确认写入介质）
```

| 调用 | 效果 |
| ---- | ---- |
| `write()` | 数据 → OS 页缓存（**内存**，不保证落盘） |
| `fflush()`（C 标准库） | 只把应用自己的 stdio 缓冲刷到内核，**同样不落盘**（常见误解） |
| `fsync(fd)` | 强制该文件数据+元数据落盘，**等磁盘确认** |
| `fdatasync(fd)` | 同上但不刷元数据，更快（MySQL 8.0 优先用于刷 redo log） |

COMMIT 的持久性保证本质上就是一次 redo log 的 fsync——它必须等真实物理写入，是全链路最慢的一步，因此高并发下 MySQL 用 **group commit** 把同一瞬间多个事务的提交合并成一次 fsync。

#### 7. COMMIT 之后 undo log 会被删吗

**最终会删，但一般不是 COMMIT 那一刻**：

- **INSERT 的 undo**：提交后基本可直接释放（新插入的行不在任何旧快照里，没人需要它）；
- **UPDATE / DELETE 的 undo**：COMMIT 后虽然不再用于回滚，但还挂着**行的旧版本供 MVCC 快照读**（别的事务可能正顺着版本链读旧值），必须等**系统中最老的活跃 ReadView** 结束后，由后台 **purge 线程**异步清理（purge 还负责物理删除打了删除标记的行）。

危害提示：只要有又老又不提交的**长事务**，最老快照推不动，purge 被卡住 → undo 表空间持续膨胀、版本链越拉越长、快照读变慢。`SHOW ENGINE INNODB STATUS` 里的 **History list length** 持续增长就是信号。

一句话：**COMMIT 后 undo 从"回滚保险"变成"MVCC 的旧版本仓库"，等最后一个需要旧版本的事务离开后才被 purge 清理。**

### 2026-09-11 数据读写路径与日志落盘顺序（WAL 细节）

#### 1. 应用读数据，读的是哪里

先分清两个容易混淆的名字：

| 名字 | 存什么 | 谁用 |
| ---- | ---- | ---- |
| **Buffer Pool** | 数据页/索引页（16KB 一页） | 读数据、改数据都走它 |
| Log Buffer | redo log 记录 | 只跟写日志有关，与读数据无关 |

**应用读数据永远从 Buffer Pool（内存）读，不存在"直接读磁盘"的常规路径**：

```text
应用 SELECT
 ├─ 目标页在 Buffer Pool？──命中（常态，99%+）──→ 直接内存返回，不碰磁盘
 └── 未命中 → 从 .ibd 整页(16KB)加载进 Buffer Pool → 再返回
```

- 缺页时加载的是**整页**而非几行（表和索引按页组织，顺带缓存整页利于后续访问）；池越大命中率越高（`innodb_buffer_pool_size` 建议物理内存 60%~80%）。
- 从页中读出的值还要过 MVCC 可见性判断：可能是当前页上的值，也可能顺版本链取旧版本（见 [[web后端开发/数据库/MySql/MVCC|MVCC]]）。

#### 2. 脏页什么时候刷盘

写数据同样是先改 Buffer Pool（变脏页），落盘异步进行，四个时机：

1. **后台 page cleaner 线程定期刷**（节奏由 `innodb_io_capacity` 控制）——日常主力；
2. **Buffer Pool 满了按 LRU 淘汰页**，被淘汰的页若是脏页必须先刷盘才能扔；
3. **redo log 快写满**（write pos 追上 checkpoint）→ 强制刷脏页推进 checkpoint（大事务卡顿的常见原因）；
4. **MySQL 正常关库时**把所有脏页刷干净。

为什么敢这么从容：redo log 在 COMMIT 时已落盘保底，脏页晚些刷，断电也能靠 redo 重放找回——**刷盘时机是性能问题，不是安全问题**。

#### 3. undo log 是实时写盘的吗

不是。**undo 页本身就是 Buffer Pool 里的普通脏页，和数据页走完全相同的异步刷盘路径**。它的安全性来自关键设计：**"往 undo 页写了什么"这件事本身也被记进 redo log**（上文旅程图的 ①②③ 全由 ④ 保底）。所以 COMMIT 时那次 redo fsync，同时给"数据修改"和"undo 修改"上了保险；宕机恢复时重放 redo 会把数据和 undo 一起重建，再用恢复出来的 undo 回滚未提交事务。

#### 4. 为什么有了 redo 还需要 undo

| | redo log | undo log |
| ---- | ---- | ---- |
| 记的内容 | 改之后的**新值**（第几页改成什么） | **反向操作 + 旧值**（怎么改回去） |
| 能做的事 | **重做**（往前放） | **撤销**（往回退） |
| 类比 | 盖楼图纸 | 拆楼图纸 |

redo 里只有新值，天生不知道"怎么改回去"。undo 的三个不可替代作用：

1. **执行中反悔**：ROLLBACK / 语句级回滚 / 死锁牺牲品回滚，用的就是 buffer pool 内存里的 undo（不依赖落盘）；
2. **宕机后清算未提交事务**：恢复时 redo 先把一切重放出来（不区分提交与否，包括未提交的修改），再由 undo 把半成品撤销——若只有 redo，未提交的修改会永久留在盘上，原子性破灭；
3. **MVCC 旧版本**：commit 后 undo 转岗为版本链仓库，直到 purge 清理（见上文第 7 条）。

关于"redo 到 commit 才保证落盘，那 undo 有什么用"的完整推演——**未提交事务的修改与它的 undo 在同一份 redo 里，同生共死**：

```text
未提交就断电：
 ├─ redo 已被提前刷盘 → 重放后"修改 + undo"都在 → 用 undo 回滚 ✓
 └─ redo 没刷盘 → 修改和 undo 一起蒸发 → 无需回滚，全当没发生 ✓
 绝不会出现"修改活着、undo 死了" → 原子性任何情况都成立
```

undo 的三段人生：**修改发生时**（内存中随时可 ROLLBACK）→ **commit 时**（随 redo 落盘转正）→ **commit 之后**（留任 MVCC 版本链，最后由 purge 退休）。

#### 5. 会不会脏页先于 redo 落盘？

不允许。WAL 的"先日志后数据页"不是约定，而是用 **LSN（日志序列号）** 强制保证的：

- 每条 redo 记录有单调递增的 LSN，每个脏页记着自己对应的最新 LSN；
- **刷脏页前检查 redo 已落盘到的 LSN，不够就先把 redo 刷过该页的 LSN，然后才写这个页**——log-before-page 被代码锁死。

反例推演（若页先落盘、redo 没落盘就断电）：盘上有了这条修改，但 redo 里没有（它的 undo 记录也没有）→ 重放无此记录、又无从回滚 → **幽灵数据永久留盘**，原子性/持久性全破。

例外（不记 redo、自然不受此约束）：临时表空间（重启后重建）、Doublewrite Buffer 自身区域（脏页先写 dblwr 区再写 .ibd 实际位置，但整体仍发生在对应 redo 落盘之后）。

### 2026-09-11 隔离级别、锁、MVCC、索引的关系（框架收敛）

总纲一句话：**隔离级别是"选多严"的需求档位；MVCC 负责"读"的隔离（读不加锁）；锁负责"写"的互斥（写写串行）；索引决定"锁得准不准"（行锁的载体）。**

#### 并发组合穷举：只有三种

| 组合 | 冲突吗 | 谁解决 |
| ---- | ---- | ---- |
| 读 — 读 | 不冲突（读不改数据） | 不用管 |
| 读 — 写 | 冲突 | **MVCC**：读旧版本快照，不加锁 |
| 写 — 写 | 冲突 | **锁**：排队串行 |

归类技巧：UPDATE / DELETE 也要"先读再写"，那个读是**当前读**，归入"写"的阵营走锁——快照读 / 当前读之分由此不必单独死记。

#### 知识归位图

```text
目标：并发处理数据，既要对（隔离级别定标准）又要快

两个工具：
  MVCC —— 管"读-写"不互相阻塞（零件：undo 版本链 + ReadView）
  锁   —— 管"写-写"排队串行  （载体：索引，决定锁一行还是全表）

一个旋钮：
  隔离级别 —— 调 MVCC 快照严格度（RC 每次拍 / RR 只拍一次）
              和锁强度（RC 只锁记录 / RR 锁到间隙防幻读 / SERIALIZABLE 读也加锁）
```

> redo / undo / Buffer Pool / fsync 属于**存储层地基**（保证又快又不丢），与本节的并发框架是上下两层，分开记。

#### 两两关系速查

| 关系 | 一句话 |
| ---- | ---- |
| 隔离级别 ↔ MVCC | 级别决定 ReadView 生成时机（RC 每次新建→不可重复读；RR 复用→可重复读）；RU 不做版本检查，SERIALIZABLE 不靠 MVCC |
| 隔离级别 ↔ 锁 | 级别越低锁越少：RC 只有记录锁；RR 有 next-key lock（记录锁+间隙锁）防幻读；SERIALIZABLE 快照读退化为锁定读 |
| 锁 ↔ MVCC | 分工：读写冲突走 MVCC（读不加锁），写写冲突走锁；快照读走 MVCC，当前读走锁 |
| 锁 ↔ 索引 | **行锁加在索引上**：有索引精确锁行；无索引全表扫描锁住所有行（近似表锁，"没走索引的 UPDATE 锁死全表"事故的根源） |
| MVCC ↔ 索引 | 版本链挂在聚簇索引行上（隐藏列 + undo）；二级索引叶子上无 trx_id，可见性判断可能要回表 |

#### 串联场景（RR 级别）

事务 A 执行 `UPDATE account SET balance = balance - 100 WHERE name = '张三'`：

1. 隔离级别 RR → 当前读 + next-key lock；
2. 锁：给张三那行加排他锁（写写互斥，别人改这行要等）；
3. 索引：name 有索引 → 只锁命中的行；无索引 → 锁全表所有行，事务 B 改任何人都被阻塞；
4. MVCC：同时事务 C 普通 `SELECT` 查张三 → 快照读旧版本，**完全不被 A 的锁阻塞**（读写互不干扰）。

防幻读是两套机制配合：当前读靠 next-key lock 锁住范围防插入（锁的活）；快照读靠 MVCC 看不到新插入的行（版本的活）。

#### 自测标准

能脱口而出："**普通读走 MVCC 快照读旧版本，不加锁；只有写和写之间才用锁串行；隔离级别决定快照拍多严、锁用多强。**"

### 2026-09-11 隔离级别的本质：MVCC 与锁规则的组合

每个隔离级别就是「MVCC 怎么读」+「锁锁多严」两个旋钮的一组预设组合：

| 级别 | 读（MVCC 规则） | 写（锁规则） | 残留问题 |
| ---- | ---- | ---- | ---- |
| RU | 不做版本检查，直接读最新版（MVCC 等于关闭） | 行锁照常（写写仍串行） | 脏读、不可重复读、幻读全有 |
| RC | **每次** SELECT 都拍新 ReadView | 只加记录锁，**没有间隙锁** | 防脏读；不可重复读、幻读还在 |
| RR（默认） | 只在**第一次** SELECT 拍 ReadView，之后复用 | next-key lock（记录锁+间隙锁） | 前两个全防；幻读基本解决 |
| SERIALIZABLE | 放弃快照读，普通 SELECT 也自动加 S 锁 | 读 S 锁 + 写 X 锁 + 间隙锁 | 全防住，并发性能最差 |

两个细节：

- RC 的「不可重复读」不是因为锁弱，而是**快照每次重拍**——每条 SELECT 都是"新世界"，别人刚提交的马上能看到；同一套 MVCC，ReadView 时机差一点，行为就差一个级别；
- 间隙锁只在 RR 及以上才有（RC 下除唯一键/外键检查外基本禁用），所以「RR 防幻读」是两件事合力：**读**靠老快照看不到新行（MVCC），**写**靠间隙锁不许往范围内插（锁）。

对称性：RU 和 SERIALIZABLE 都不用 MVCC，但方向相反——

```text
RU：           什么都不检查，读最新        → 最松（脏读）
SERIALIZABLE： 不信快照，读也上锁走串行    → 最严（等于回到纯加锁数据库）
RC / RR：      中间态，靠 ReadView 拍照时机区分
```

四个级别不是孤立设定，而是「从全关到全开」的一条光谱。
