# 索引

索引（Index）是帮助 MySQL **高效获取数据的有序数据结构**（官方手册 8.3 Optimization / 8.8 EXPLAIN）。无索引时查找只能全表扫描；有索引时按有序结构定位，代价是额外的存储空间和写入维护成本（索引列 DDL 语句见 [[web后端开发/数据库/MySql/DDL|DDL]]）。

## 一、为什么是 B+ 树

MySQL 将数据存于磁盘，以**页（16KB）**为单位读取，因此树越矮、IO 次数越少。各候选结构的缺陷：

| 结构 | 问题 |
| ---- | ---- |
| 二叉搜索树 | 顺序插入时退化为链表 |
| 红黑树（自平衡二叉树） | 仍只有二叉，数据量大时树太高，IO 次数多 |
| Hash 表 | 等值查询 O(1) 很快，但**不支持范围查询和排序**（Memory 引擎 / InnoDB 自适应哈希使用） |
| B 树 | 非叶子节点也存数据，单页容纳的键少，树更高 |
| **B+ 树** | 非叶子节点只存键（路更多、树更矮）；叶子节点存数据且用**双向链表**串联（范围查询、排序友好） |

容量估算：非叶子节点存「主键 bigint（8B）+ 页指针（6B）」，一页约 1170 个指针；叶子页按每行 1KB 可存 16 行。则**三层 B+ 树可存约 1170 × 1170 × 16 ≈ 2000 万行**，即一次主键查询最多 3~4 次页 IO。

## 二、索引分类

按物理存储结构（InnoDB）：

- **聚簇索引（主键索引）**：叶子节点存放**整行数据**。InnoDB 表数据本身就是按主键组织的 B+ 树（索引即数据）。建表时若不定义主键，则选择第一个非空唯一索引，都没有时用隐藏的 `DB_ROW_ID` 生成。
- **二级索引（辅助索引）**：叶子节点存放**索引列 + 主键值**。

按功能逻辑：

| 类型 | 关键字 | 说明 |
| ---- | ---- | ---- |
| 主键索引 | PRIMARY KEY | 聚簇索引，一张表一个 |
| 唯一索引 | UNIQUE | 值唯一，可为 NULL |
| 常规索引 | INDEX / KEY | 无限制，仅加速 |
| 全文索引 | FULLTEXT | 分词匹配文本 |
| 联合索引 | — | 多列组成一个索引，如 `INDEX(a, b, c)` |

### 回表与覆盖索引

- **回表**：通过二级索引只拿到主键值，还需要再到聚簇索引中查一次整行数据。二级索引查询默认要回一次表。
- **覆盖索引**：查询所需的列全部包含在索引中，无需回表（EXPLAIN 的 Extra 显示 `Using index`）。例如联合索引 `(name, phone)` 上执行 `SELECT name, phone ... WHERE name = 'x'`。这是索引设计的重要优化手段。

## 三、索引语法

```sql
CREATE [UNIQUE] INDEX idx_user_phone ON tb_user(phone);
CREATE INDEX idx_user_name_age ON tb_user(name, age);   -- 联合索引

SHOW INDEX FROM tb_user;                                 -- 查看已有索引
DROP INDEX idx_user_phone ON tb_user;

-- SQL 提示（人工干预优化器选择）
SELECT * FROM tb_user USE INDEX(idx_a) WHERE ...;        -- 建议使用
SELECT * FROM tb_user IGNORE INDEX(idx_a) WHERE ...;     -- 忽略
SELECT * FROM tb_user FORCE INDEX(idx_a) WHERE ...;      -- 强制使用
```

## 四、最左前缀法则

联合索引 `(a, b, c)` 相当于建了 `(a)`、`(a,b)`、`(a,b,c)` 三套有序规则，查询条件必须**从最左列开始连续命中**：

```sql
WHERE a = 1 AND b = 2 AND c = 3   -- 走 a、b、c
WHERE a = 1 AND b = 2             -- 走 a、b
WHERE b = 2 AND c = 3             -- 不走该索引（缺了 a）
WHERE a = 1 AND c = 3             -- 只走 a（中间断档，c 用不上索引定位）
```

- 条件书写的先后顺序不影响（优化器会调整）。
- **范围查询右侧的列索引失效**：`WHERE a > 1 AND b = 2` 只有 a 走索引（范围之后无序）。
- 把等值条件的列放在联合索引前面、范围条件的列放最后。

## 五、索引失效场景

```sql
-- 1. 索引列参与运算或函数
WHERE id + 1 = 10;                        -- 失效，应为 WHERE id = 9
WHERE SUBSTRING(name, 1, 2) = '张三';       -- 失效

-- 2. 字符串列不加引号（触发隐式类型转换，等价于对索引列套函数）
WHERE phone = 13800001234                 -- phone 为 varchar，失效

-- 3. LIKE 以 % 开头
WHERE name LIKE '%三'                     -- 失效；'三%' 不失效

-- 4. OR 两侧任一列没有索引 → 整体全表扫描

-- 5. 违反最左前缀（见上）
```

- `IS NULL`、`!=`、`NOT IN` 是否走索引**取决于数据分布**：若需扫描的行占比过高，优化器会直接全表扫描（回表逐行查不如顺序扫全表）。用 EXPLAIN 验证。

## 六、EXPLAIN 执行计划

`EXPLAIN SELECT ...;` 查看优化器生成的执行计划，重点字段：

| 字段 | 说明 |
| ---- | ---- |
| id | SELECT 序号，id 越大越先执行；相同则从上往下 |
| type | 访问类型，性能从好到差：`system > const(主键/唯一键等值) > eq_ref(join 主键) > ref(普通索引等值) > range(范围) > index(扫全索引) > ALL(全表扫描)`；生产要求至少 range 级别 |
| possible_keys / key | 可能用到的索引 / 实际用到的索引（NULL 即全表扫描） |
| key_len | 实际使用的索引字节数，可推断联合索引用了几列 |
| rows | 预估扫描行数 |
| Extra | `Using index` 覆盖索引；`Using index condition` 索引下推（ICP，8.0 默认开启，在索引层先过滤二级条件再回表）；`Using filesort` / `Using temporary` 出现时需优化排序与分组 |

## 七、索引设计准则

**适合建**：WHERE、ORDER BY、JOIN、GROUP BY 涉及的列；高频查询的覆盖场景（用联合索引避免回表）；唯一性好的列（区分度高）。

**不适合建**：数据量小、频繁更新的表；区分度低的列（如性别）；很少被查询的列；已有大量冗余组合的索引。

索引的代价：占用磁盘空间；INSERT / UPDATE / DELETE 需要同步维护 B+ 树，降低写性能——索引并非越多越好。
