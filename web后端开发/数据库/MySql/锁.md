# 锁

锁用于协调多个事务/会话并发访问同一资源，保证数据一致性（官方 15.7.1 InnoDB Locking）。按**粒度**从大到小分为全局锁、表级锁、行级锁；行级锁按**模式**分为共享锁（S）与排他锁（X）。

## 一、全局锁

锁定整库，所有表只读：

```sql
FLUSH TABLES WITH READ LOCK;   -- 加锁
UNLOCK TABLES;                 -- 解锁
```

用于**全库逻辑备份**。备份期间业务完全不能写，InnoDB 场景更常用 `mysqldump --single-transaction`，借助 MVCC 在一致性快照上导出，不阻塞业务。

## 二、表级锁

### 1. 表锁

```sql
LOCK TABLES t READ;            -- 读锁：所有会话可读，不可写
LOCK TABLES t WRITE;           -- 写锁：仅当前会话可读写
```

粒度粗、冲突概率高，InnoDB 一般不用（MyISAM 只有表锁）。

### 2. 元数据锁（MDL）

系统**自动加**，无需显式使用：执行 DML（增删改查）时加 MDL **读锁**，执行 DDL（改表结构）时需要 MDL **写锁**。作用是避免「查询进行中表结构被改」。注意：MDL 写锁会排队等待所有读锁释放，若此时有长事务/慢查询持有读锁，后续所有请求（哪怕普通 SELECT）都会被阻塞，可能压垮数据库。

### 3. 意向锁（Intention Lock，IS / IX）

表级锁，由 InnoDB 在给行加 S / X 锁**前自动**先在表上加意向锁：

- 作用：事务想锁整张表时，只需检查表上有没有意向锁，而**不必逐行检查行锁**，减少加表锁的开销。
- 意向锁之间互相兼容，与表级 S / X 锁互斥；它不阻塞任何行级操作。

### 4. AUTO-INC 锁

自增列取值时短暂持有，保证自增值连续分配（`innodb_autoinc_lock_mode` 控制）。

## 三、行级锁（InnoDB）

InnoDB 行锁是加在**索引记录**上的；如果 SQL 没走索引（或索引失效），将扫描并锁定全表所有记录，效果接近锁表。三种实现：

### 1. 记录锁（Record Lock）

锁定索引上的**单条记录**：

```sql
-- id 为主键，仅阻塞其他事务对 id=1 行的写与锁定读
SELECT * FROM account WHERE id = 1 FOR UPDATE;
```

### 2. 间隙锁（Gap Lock）

锁定索引记录之间的**开区间**（如 id 值 1、5、10 存在时，间隙为 (1,5)、(5,10)、(10,+∞)），**仅在 RR 隔离级别**下生效。间隙之间、间隙与记录锁之间互不冲突，但会**阻止其他事务在间隙内插入**数据——这是 RR 防幻读的关键（RC 级别没有间隙锁，因此有幻读）。

### 3. 临键锁（Next-Key Lock）

**记录锁 + 间隙锁**的组合，锁定**左开右闭区间**，是 InnoDB 在 RR 下的默认行锁形式：

```sql
-- 表中 id 有 1、5、10，执行：
SELECT * FROM emp WHERE id > 5 FOR UPDATE;   -- 锁住 (5,10]、(10,+∞)
-- 其他事务无法插入 id 在 (5,+∞) 的任何行，也无法修改/删除 id=10
```

另有**插入意向锁**：事务插入前在目标间隙上的标记，与间隙锁冲突（间隙锁存在时插入被阻塞）。

### 加锁语句对照

| 语句 | 加锁 |
| ---- | ---- |
| 普通 SELECT | 不加锁（MVCC 快照读，见 [[web后端开发/数据库/MySql/MVCC\|MVCC]]） |
| UPDATE / DELETE / INSERT | X 记录锁（范围条件在 RR 下为临键锁） |
| SELECT ... FOR UPDATE | X 锁（当前读） |
| SELECT ... FOR SHARE | S 锁 |

S 锁与 S 锁兼容；S 与 X、X 与 X 互斥。

## 四、死锁

两个事务互相持有对方需要的锁并互相等待：

```sql
-- 事务A：UPDATE ... WHERE id = 1;  → 持有 id=1 的锁
-- 事务B：UPDATE ... WHERE id = 2;  → 持有 id=2 的锁
-- 事务A：UPDATE ... WHERE id = 2;  → 等待B释放
-- 事务B：UPDATE ... WHERE id = 1;  → 等待A释放  → 死锁
```

处理与预防：

- InnoDB 开启死锁检测（`innodb_deadlock_detect` 默认 on），发现死锁后**回滚代价较小的事务**；也可等待锁超时（`innodb_lock_wait_timeout` 默认 50 秒）。
- 排查：`SHOW ENGINE INNODB STATUS;` 查看最近一次死锁日志。
- 预防：事务按**相同顺序**访问表和行；事务尽量小、及时提交；同一事务中避免混入交互等待；用索引避免行锁升级为锁全表记录。

## 五、悲观锁与乐观锁

这是并发控制的两种**应用层思想**，不是 MySQL 的锁类型：

- **悲观锁**：假设冲突经常发生，取数时就加锁：`SELECT ... FOR UPDATE`，其他事务阻塞等待。
- **乐观锁**：假设冲突很少发生，更新时用版本号/CAS 校验：

```sql
-- 读出 version=5 后提交更新，失败则说明被并发修改过，重试
UPDATE t SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;   -- 影响行数为 0 即更新失败
```

读多写少用乐观锁，写冲突激烈用悲观锁。
