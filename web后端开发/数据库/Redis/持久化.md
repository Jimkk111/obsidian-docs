# 持久化

Redis 数据在内存中，重启即丢失。持久化机制把内存数据落盘，重启时恢复。两种方案：**RDB** 快照、**AOF** 命令日志（可组合为混合持久化）。

## RDB（Redis Database）

**定时快照**：某一时刻全部内存数据以二进制形式写入磁盘文件（默认 `dump.rdb`，`dbfilename` / `dir` 配置）。

触发方式：

- 手动：`SAVE`（**阻塞**主线程，禁用）/ `BGSAVE`（fork 子进程写，推荐）。
- 自动：`save` 规则触发（如 Redis 7 默认 `3600 1 / 300 100 / 60 10000`：3600 秒内 1 次修改、300 秒内 100 次、60 秒内 10000 次；Redis 6 为 `900 1 / 300 10 / 60 10000`）。
- 正常 shutdown、主从**全量同步**时也会生成。

### BGSAVE 原理（写时复制 Copy-On-Write）

1. 主进程 `fork()` 出子进程，父子共享同一块物理内存（只读）。
2. 子进程遍历内存数据生成临时 RDB 文件，完成后**原子替换**旧文件。
3. fork 之后主进程若有新写入，操作系统会**复制对应的内存页**再写（写时复制），子进程看到的仍是 fork 瞬间的快照。

> fork 本身需复制页表，数据量大时会短暂阻塞主线程；写时复制期间新写入越多，额外内存占用越大。

优缺点：文件**紧凑、恢复快**（直接载入二进制）；但快照间隔内的数据宕机即丢，无法做到秒级安全。

## AOF（Append Only File）

**追加命令日志**：每条写命令执行成功后追加到 AOF 文件（默认 `appendonly.aof`），重启时**重放**命令恢复数据。

默认**关闭**（`appendonly no`，Redis 8 仍然如此），开启：

```conf
appendonly yes
appendfilename "appendonly.aof"
```

### 刷盘策略 appendfsync

| 策略 | 行为 | 最多丢失 | 性能 |
| ---- | ---- | ---- | ---- |
| always | 每条写命令都 fsync | 1 条命令 | 慢 |
| **everysec（默认）** | 每秒 fsync 一次 | 1 秒数据 | 折中 |
| no | 交给 OS（约 30s） | 不确定 | 快 |

> AOF 文件末尾损坏（断电）时，可用官方工具修复：`redis-check-aof --fix appendonly.aof`。

### AOF 重写

命令不断追加，文件无限膨胀（100 次 `INCR` 等价于 1 句 `SET`）。**AOF 重写**：fork 子进程，根据**当前内存的最终状态**生成一份等价的最小命令集写入新文件；重写期间的新命令同时写入 AOF 缓冲区和重写缓冲区，完成后把增量追加进新文件并原子替换。

- 手动：`BGREWRITEAOF`。
- 自动：`auto-aof-rewrite-percentage 100`（比上次重写后大 100%）且 `auto-aof-rewrite-min-size 64mb`。
- Redis 7.0 起为 multi-part AOF：base（全量）+ incr（增量）多个文件 + manifest 清单，重写只需替换 base（了解）。

## RDB vs AOF

| 对比项 | RDB | AOF |
| ---- | ---- | ---- |
| 持久化内容 | 定时全量二进制快照 | 每条写命令 |
| 文件大小 | 小 | 大（可重写压缩） |
| 恢复速度 | 快（直接载入） | 慢（逐条重放） |
| 数据安全性 | 可能丢最后一次快照后的数据 | everysec 最多丢 1 秒 |
| 运行开销 | 平时几乎无，fork 瞬间有 | 持续小幅写盘 |

## 混合持久化（4.0+，推荐）

`aof-use-rdb-preamble yes`（5.0+ 默认开启）。开启后 **AOF 重写时**：新文件前半段写 **RDB 格式**的全量快照，之后的增量写 **AOF 命令格式**。恢复时先载入 RDB 快速恢复大部分数据，再重放少量增量命令——兼得 RDB 的恢复速度和 AOF 的数据安全。

> 生产常用组合：`appendonly yes` + `appendfsync everysec` + 混合持久化开启。
