# 缓存

缓存是 Redis 最核心的使用场景：读多写少的热点数据放内存，高并发下挡住绝大多数读请求，降低 MySQL 压力、缩短响应时间（典型如店铺信息、商品详情）。

## 读写模式：旁路缓存（Cache Aside）

最常用的模式，应用层同时操作缓存与数据库。

**读**：

1. 读缓存，命中直接返回。
2. 未命中 → 查数据库 → 结果写入缓存（**设置 TTL**）→ 返回。

**写（更新数据）**：**先更新数据库， 再删除缓存**。

### 为什么是「删缓存」而不是「更新缓存」

- 并发写时两个更新交错，缓存里算出的值可能与数据库乱序不一致。
- 惰性加载：删除后下一次读触发回源；写多读少的数据不必白白维护缓存。

### 为什么「先库后缓存」

- **先删缓存**：删除后另一线程读未命中、回源读到**旧值**写回缓存 → 脏数据概率高。
- **先库后删**：理论上仍有极小概率不一致（读线程查库后、写缓存前恰好穿插一次写操作），但要求读写耗时精确交错，概率很低。缓存架构的目标是**最终一致**，而不是强一致。

### 缓存一致性

即便「先库后删」，仍存在脏数据窗口：线程 A 读未命中查到旧值 → 线程 B 更新库并删缓存 → A 把**旧值写回缓存**，不一致将持续到 TTL 到期。

增强手段：

- **延迟双删**：删缓存 → 更新数据库 → 延迟数百毫秒（覆盖一次读回源耗时）→ **再删一次缓存**。
- **订阅 binlog 异步删缓存**：用 Canal 等组件订阅 MySQL binlog，数据变更后异步删除缓存——业务代码零侵入、可靠性高（推荐）。
- 强一致需求只能加读写锁 / 分布式锁串行化（性能差，慎用）。

## 缓存穿透

**请求的数据在缓存和数据库中都不存在**（如恶意传 id = -1），缓存永不生效，每次请求都打到数据库。

解决方案：

| 方案 | 做法 | 优缺点 |
| ---- | ---- | ---- |
| 缓存空值 | 查库无结果时缓存 `""` 并设**短 TTL**（如 60s） | 简单；额外内存、可能有短暂不一致 |
| 布隆过滤器 | 启动时把存在的 key 全量载入；请求先过过滤器：**判定不存在 → 一定不存在，直接拒绝**；可能存在 → 放行去查 | 内存极省；有低误判率（把不存在的判为存在，无害）、不支持删除、维护成本 |
| 参数校验 / 限流 | id ≤ 0 直接拒绝；接口限流、风控 | 第一道防线 |

## 缓存击穿

**热点 key 在过期的一瞬间**，大量并发同时未命中、同时回源查库，数据库瞬间压力激增。

| 方案 | 做法 | 特点 |
| ---- | ---- | ---- |
| 互斥锁 | 回源前 `SETNX` 抢锁，抢到的线程查库重建缓存，其余线程等待重试 | 保证一致；牺牲可用性（等待） |
| 逻辑过期 | 不设 TTL；value 里额外存一个过期时间字段；读到「已逻辑过期」→ 抢锁异步重建，期间**返回旧数据** | 保证可用；重建期间返回旧值 |

## 缓存雪崩

**同一时间段大量 key 同时过期**，或 **Redis 实例宕机**，请求洪峰直接砸向数据库。

解决方案：

- 大量 key 同时过期：TTL 加**随机值**（如 30min + random(0~10min)）；热点数据预热 + 逻辑过期/不设 TTL。
- Redis 宕机：搭建高可用（主从 + 哨兵/集群，见 [[web后端开发/数据库/Redis/主从与集群|主从与集群]]）；服务侧限流、熔断、降级；多级缓存（本地 Caffeine + Redis）。

## 三者对比

| 问题 | 触发原因 | 核心解法 |
| ---- | ---- | ---- |
| 穿透 | 数据**不存在**，缓存永不生效 | 空值缓存 / 布隆过滤器 / 参数校验 |
| 击穿 | **热点 key 过期瞬间**高并发回源 | 互斥锁 / 逻辑过期 |
| 雪崩 | **大量 key 同时过期**或实例宕机 | 随机 TTL / 高可用 / 限流降级 |

## 实践清单

- key 命名规范、所有缓存都设 TTL 并加随机抖动。
- 更新走「先库后删」，重要数据叠延迟双删或 binlog 订阅。
- 热点数据提前预热；避免大 key（单 value 控制在几十 KB 内）、热 key 集中问题。
- 任何缓存方案都要有兜底：即使不一致，TTL 到期也能自愈。
