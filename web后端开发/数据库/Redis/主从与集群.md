# 主从复制、哨兵与分片集群

单机 Redis 的两个问题：**宕机即不可用**、**读写量与存储量受单机上限**。架构演进：主从复制 → 哨兵 → 分片集群。

## 主从复制（Replication）

**一主多从**：主库负责写，从库负责读（读写分离、数据热备）。从库默认只读（`replica-read-only yes`）。

搭建：在从库配置文件或运行时执行

```conf
replicaof <主库ip> <主库端口>     # Redis 5.0 之前叫 slaveof；取消：replicaof no one
```

### 同步原理（面试重点）

主从各自维护两个关键量：**replication id（replid，主库数据集的版本标识）** 与 **offset（复制偏移量，累计写入的字节数）**。从库凭 `(replid, offset)` 判断该做全量还是增量同步。

**全量同步**（第一次连接，或断线过久）：

1. 从库首次连接主库，发送 `psync ? -1`。
2. 主库回复 `FULLRESYNC <replid> <offset>`，执行 **bgsave** 生成 RDB 发给从库。
3. 期间主库的新写命令暂存 **repl_baklog（复制缓冲区）**。
4. 从库清空本地数据、载入 RDB，再接收缓冲区中的增量命令。

**增量同步**（短暂断线后重连）：

1. 从库发送 `psync <replid> <offset>`。
2. 若 offset 之后的数据还在 repl_baklog 中 → 主库只补发差量。
3. 若 repl_baklog 是**环形缓冲区**（默认 1mb，`repl-backlog-size`），断线期间数据已被覆盖 → 退化为**全量同步**。

> 主从延迟：从库异步复制，可能读到稍旧数据。主库宕机需**手动**执行 `replicaof no one` 切主——这就是哨兵要解决的问题。

## 哨兵（Sentinel）

哨兵是**独立进程**（默认端口 26379，不存数据），职责：**监控、通知、自动故障转移**。通常部署奇数个（≥3）互相监督。

```conf
# sentinel.conf
sentinel monitor mymaster 192.168.1.10 6379 2    ; 监控名为 mymaster 的主库，quorum = 2
sentinel down-after-milliseconds mymaster 5000   ; 5 秒无响应判定下线
```

### 故障转移流程（面试重点）

1. **主观下线（sdown）**：单个哨兵 ping 主库超时，自己认为它下线。
2. **客观下线（odown）**：该哨兵询问其他哨兵，**≥ quorum** 个都认为下线 → 确认下线（防止单个哨兵网络抖动误判）。
3. **选举哨兵 leader**：哨兵之间投票选出 leader 执行故障转移（Raft 思想，先到先得拉票，需多数派）。
4. leader 挑选新主库：① `replica-priority`（优先级）越小越优先（0 表示不参与）② 复制 **offset** 越大（数据越新）越优先 ③ **runid** 最小。
5. 执行切换：选中从库执行 `replicaof no one` 升主，其余从库 `replicaof` 指向新主；旧主恢复后自动降为从库。哨兵通过**发布订阅**通知客户端新主地址。

## 分片集群（Redis Cluster）

哨兵解决了可用性，但**写并发与存储容量仍受单机限制**。Cluster 把数据**分片**到多个主节点：

- 多个主节点（每个主配从节点），**没有独立哨兵**——节点间通过 **gossip 协议**互相通信、监控，自动完成主从切换。
- **16384 个哈希槽（slot）**：`slot = CRC16(key) % 16384`，每个主节点负责一段槽区间。key 按 hash 决定落在哪个节点。
- 客户端可连任意节点：请求的 key 不归它管时返回 **MOVED 重定向**（智能客户端本地缓存槽映射表）。
- 多 key 命令要求 key 在**同一个槽**：可用 **hash tag** 强制同槽——key 中 `{}` 内的内容才参与 hash，如 `{u1001}:cart` 与 `{u1001}:orders`。

搭建（了解）：每个节点 `cluster-enabled yes`，然后：

```bash
redis-cli --cluster create ip1:6379 ip2:6379 ip3:6379 ip4:6379 ip5:6379 ip6:6379 --cluster-replicas 1
```

> **面试：为什么是 16384 个槽？**（作者 antirez 的回答）① CRC16 产生 16 位（65536），但节点间心跳要携带槽位图，16384 位 = 2KB 大小合适，65536 太大；② 官方建议集群不超过 1000 个节点，16384 个槽足够；③ 槽越少（如 16384 以下）节点多时位图压缩效果差。

## 三种架构对比

| 架构 | 解决的问题 | 说明 |
| ---- | ---- | ---- |
| 主从复制 | 读写分离、数据热备 | 主宕机需手动切换 |
| 哨兵 | 自动故障转移、高可用 | 仍是单主写，容量受限 |
| 分片集群 | 水平扩容（写 + 存储）、高可用 | 数据分片，客户端感知槽 |
