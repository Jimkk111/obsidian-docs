# 分布式锁

## 为什么需要分布式锁

服务**集群部署**（多个 JVM 实例）时，JVM 本地锁（`synchronized` / `ReentrantLock`）只能锁住本进程，跨节点的并发拦不住。Redis 命令单线程执行，`SETNX` 天然只有一个客户端能成功——借它实现**跨 JVM 的互斥**。

经典案例：秒杀「一人一单」，100 个请求打到 3 个节点，本地锁各锁各的，仍会超卖 / 重复下单；必须所有节点先抢同一把 Redis 锁。

## 基本实现与两个必须解决的坑

```bash
SET lock:order:1 thread1 NX EX 10    # 不存在才能设置成功 = 抢到锁；同时设置过期时间
... 临界区业务（校验 + 下单） ...
DEL lock:order:1                     # 释放锁
```

1. **必须一条命令完成「加锁 + 过期」**：早期 `SETNX` + `EXPIRE` 是两条命令，若客户端在两步之间崩溃，锁永不过期 → **死锁**。`SET key value NX EX 10` 一条命令原子完成（面试常考）。
2. **误删他人锁**：线程 1 业务超时，锁到期自动释放；线程 2 抢到锁，随后线程 1 执行完 `DEL` → **删掉了线程 2 的锁**，线程 3 趁虚而入。
	- 解决：加锁时 value 存**线程标识**（`UUID + threadId`，集群内唯一）；释放时**校验是自己的锁才删**。
	- 「读取 + 比对 + 删除」必须原子 → 用 **Lua 脚本**（见 [[web后端开发/数据库/Redis/事务与Lua|事务与Lua]]）：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

至此仍有三个问题：① 业务没执行完锁先过期（过期时间难估）② 不可重入 ③ 不可等待重试 → **Redisson**。

## Redisson

功能完善的 Redis Java 框架，`RLock` 逐项解决上述问题（底层大量使用 Lua 保证原子性）：

1. **可重入**：锁结构是 **Hash**——field 存锁标识（UUID:threadId），value 存**重入计数**；同一线程再次加锁计数 +1，解锁 -1，减到 0 才真正删除 key（思想同 `ReentrantLock`）。
2. **看门狗（watchdog）续期**：加锁**不指定 leaseTime** 时，锁的过期时间默认 30s（`lockWatchdogTimeout`），后台任务每 10s（1/3）检查：线程仍持锁就**重置为 30s**——业务没跑完锁不会过期；进程宕机则看门狗随进程消失，锁到期自动释放，不会死锁。
3. **可重试**：`tryLock(waitTime)` 基于发布订阅实现——锁释放时发布消息，唤醒等待线程重新抢锁，而非自旋空转。
4. **主从一致性**：主从架构下，主库写入锁后尚未同步给从库就宕机，新主上没有这把锁 → 另一个客户端又能加锁。可选方案：**MultiLock**（向所有节点独立加锁的联锁）、**RedLock**（多数派加锁成功才算持有；社区存在争议——Martin Kleppmann 质疑其依赖时钟假设，作者 antirez 回应过）。对一致性要求极高的锁可用 ZooKeeper 实现。

Spring Boot 使用：

```xml
<dependency>
    <groupId>org.redisson</groupId>
    <artifactId>redisson-spring-boot-starter</artifactId>
</dependency>
```

```java
RLock lock = redissonClient.getLock("lock:order:" + userId);
boolean ok = lock.tryLock(5, TimeUnit.SECONDS);   // waitTime=5s；不传 leaseTime → 触发看门狗
if (!ok) {
    return "操作太频繁，请稍后再试";
}
try {
    // 临界区：校验 + 下单
} finally {
    if (lock.isHeldByCurrentThread()) {   // 只释放自己持有的锁
        lock.unlock();
    }
}
```

> 注意：一旦指定 leaseTime，看门狗即失效（到点自动过期，业务没跑完锁会被别人抢走）。

## Redis 锁 vs ZooKeeper 锁

| | Redis | ZooKeeper |
| ---- | ---- | ---- |
| 模型 | AP，性能高 | CP，一致性强 |
| 实现 | SET NX + 过期 + Lua | 临时顺序节点 + watch 监听前驱 |
| 风险 | 主从切换等极端情况可能丢锁 | session 超时误释放等，性能较低 |

绝大多数业务用 Redis 锁即可；对锁的正确性要求极端严格（钱、库存不准不可接受）时再考虑 ZooKeeper 或数据库乐观锁兜底。
