# 并发一致性概念的时间线拆解

## 问题/背景

学前端转全栈时，被一堆"高级概念"劝退：N+1、原子更新、锁、缓存一致性、MVCC、幂等、分布式锁、CAP……名词背不完，且不理解"怎么导致的、具体怎么解决"。教程把概念和注解混在一页讲，加剧了混乱感。

## 原因分析

这几十个名词背后其实只有**六个根因**，概念是"前人踩坑经验的压缩包"，没踩过坑去背 = 拿到压缩文件但没有解压密码。正确路径是先见到问题的时间线，再学概念。

六个根因：
1. **操作之间有时间差**（并发）→ 丢失更新、唯一性竞态、悲观锁/乐观锁/CAS、死锁、隔离级别、MVCC、分布式锁、幂等
2. **数据存了不止一份**（副本）→ 缓存穿透/击穿/雪崩、缓存一致性、延迟双删、主从复制、读写分离、反范式
3. **单机扛不住**（量）→ 索引、慢查询、深分页、分库分表、负载均衡
4. **机器和网络会挂**（故障）→ 超时、重试、降级、熔断、限流、健康检查、高可用
5. **跨机器调用**（分布式）→ 分布式事务、CAP、最终一致性、消息队列
6. **不怀好意的输入**（安全）→ 注入、越权、哈希与加密、JWT、CORS

## 解决方案

用**时间线（t1/t2/t3）**还原每个概念"怎么导致的"，五个核心概念都是同一个母题——"读和写之间有时间差，别的请求会插进来"：

**① 丢失更新（原子更新）**
```
t1: 请求A 查到 views=100
t2: 请求B 查到 views=100     ← A 还没写回
t3: 请求A 写回 101
t4: 请求B 写回 101           ← A 的 +1 被覆盖
```
解法：把"读算写"压进数据库一步 → `UPDATE news SET views = views + 1 WHERE id = ?`

**② 唯一性竞态（锁的引子）**
```
t1: A 查用户名 tom → 不存在
t2: B 查 tom → 不存在
t3: A INSERT ✓
t4: B INSERT ✓              ← 重复了
```
解法选型口诀（代价递增）：唯一索引 + 捕获 `DuplicateKeyException` → 原子 SQL → 乐观锁（version 字段）→ 悲观锁（`FOR UPDATE`）。

**③ N+1（不是并发问题，是循环付费）**
列表 20 条，循环里逐条查关联 → 1+20=21 次网络往返。解法：JOIN / `WHERE id IN` 批量 / 窗口函数，一次查回内存对号入座。

**④ 缓存一致性（一份数据两处存）**
最阴险的交错：读请求查库拿到旧值 → 写请求更新库并删缓存 → 读请求把**旧值回填**缓存。解法：写时删缓存（不更新缓存）+ TTL 兜底（脏得有界）+ 延迟双删（删完 1 秒再删一次，清掉迟到的回填）。认知：缓存本来就是拿一致性换性能。

**⑤ MVCC（数据库内部机制，无需操作）**
写未提交时读会阻塞 → 数据库保留多版本，读方读"最近已提交版本"，读写互不阻塞。面试答"多版本 + 读不加锁 + RR/RC 区别在读哪个版本"即可。

## 关键代码/命令

```sql
-- 原子更新（对读改写丢失）
UPDATE news SET views = views + 1 WHERE id = ?;

-- 幂等写入（对唯一性竞态，配合 uk_user_news 唯一索引）
INSERT INTO history (user_id, news_id, viewed_at)
VALUES (?, ?, NOW())
ON DUPLICATE KEY UPDATE viewed_at = NOW();

-- 乐观锁（对复杂对象并发改）
UPDATE t SET x=?, version=version+1 WHERE id=? AND version=旧version;
```

## 经验教训

- **按症状认领概念**，不要按清单背：接口慢→N+1/索引；数字对不上→并发写；显示旧数据→缓存一致性；重复数据→唯一性竞态；对方挂了拖死你→超时/熔断；一次操作执行两次→幂等。
- 概念的合法学习路径是"先见到尸体再学破案"——亲手复现（两个终端并发 curl 100 次看 views 加没加满）胜过读十篇博客。
- 面试答题模板：**结论 → 原理一句话 → "我项目里就是这么用的，比如……"**。
- 实习生边界：①④ 真懂、②⑤⑥ 知道名字和一句话即可；没实践过的答"项目规模没用到，但我理解它解决什么问题"，诚实比硬撑安全。
