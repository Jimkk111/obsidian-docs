## 一、声明式事务

经典案例——转账：扣钱和加钱必须同生共死，中间任何一步失败就要整体回滚。

```java
@Service
@RequiredArgsConstructor
public class AccountService {

    private final AccountMapper accountMapper;

    @Transactional(rollbackFor = Exception.class)     // 就这一行
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        accountMapper.decrease(fromId, amount);       // 第一步：扣钱
        // 假如这里抛异常……
        accountMapper.increase(toId, amount);         // 第二步：加钱
    }
}
```

原理是 [[web后端开发/JavaWeb/springboot/spring/AOP|AOP]]：Spring 给这个类生成代理，方法执行前开事务，正常结束提交，抛异常回滚。**业务代码完全无感**，这叫声明式事务。

Spring Boot 项目引入 `mybatis-spring-boot-starter` 或 `spring-boot-starter-jdbc` 后事务管理器已自动配置好，**拿来就用，零配置**。

## 二、@Transactional 放哪、怎么写

- **加在 Service 的方法上**（推荐）或类上（类里所有 public 方法都生效）
- 不要加到 Controller/Mapper 上——事务属于业务层职责
- 常用参数：

```java
@Transactional(
    rollbackFor = Exception.class,     // 见下，永远写上它
    propagation = Propagation.REQUIRED,// 传播行为，默认值，见下
    isolation = Isolation.DEFAULT,     // 隔离级别，用数据库默认（InnoDB 可重复读）
    timeout = 5,                       // 超时秒数，防长事务
    readOnly = true                    // 只读事务，纯查询可加，有轻微优化
)
```

⚠️ **rollbackFor 必须写**：默认只回滚 `RuntimeException` 和 `Error`。抛出受检异常（如 `IOException`、自定义 `extends Exception` 的异常）时**不会回滚**——恰好坑住"自定义异常继承 Exception"的新手。写 `rollbackFor = Exception.class` 一劳永逸。

## 三、传播行为（重点掌握两个）

一个事务方法 A 调用另一个事务方法 B 时，B 怎么处理"外层已经有事务"这件事：

| 传播行为 | 含义 | 典型场景 |
|---|---|---|
| `REQUIRED`（默认） | 有事务就加入，没有就新建 | 99% 的场景，不用动 |
| `REQUIRES_NEW` | 挂起当前事务，**永远自己开新的** | 主流程失败也不能影响的独立动作：记操作日志、发通知 |
| `SUPPORTS` | 有就加入，没有就非事务跑 | 查询 |
| `NOT_SUPPORTED` | 挂起事务，非事务跑 | 不该在事务里的耗时操作（发邮件等） |
| `MANDATORY` | 必须已有事务，否则报错 | 强制被别的事务调用 |
| `NEVER` | 必须没有事务，否则报错 | 少用 |
| `NESTED` | 嵌套事务（保存点），可局部回滚 | 少用 |

```java
@Service
public class LogService {
    @Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
    public void saveLog(String msg) { ... }   // 自己开新事务：主流程回滚，日志照样落库
}
```

## 四、失效场景 ⚠️（高频考点，也最坑）

`@Transactional` 靠 AOP 代理工作，**凡是绕过代理的调用都会让它失效**：

```java
@Service
public class OrderService {

    // ❌ 失效 1：自调用。this.update() 是原始对象调方法，没走代理
    public void create() {
        this.update();
    }

    @Transactional(rollbackFor = Exception.class)
    public void update() { ... }   // ❌ 失效 2：方法不是 public
}
```

完整清单：

1. **同类自调用**——`this.update()` 不经过代理，最常见；解法：把方法拆到另一个 Bean，或注入自身代理（`AopContext.currentProxy()`）
2. **方法不是 public**——非 public 方法代理拦不到
3. **异常被 try-catch 吞了**——代理感知不到异常，照常提交：

```java
    @Transactional(rollbackFor = Exception.class)
    public void transfer(...) {
        try {
            accountMapper.decrease(...);
            int x = 1 / 0;
        } catch (Exception e) {
            log.error("出错了", e);        // ❌ 吞掉异常 = 不回滚
        }
    }
    // 想捕获又想回滚：catch 里手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    // 或者捕完再 throw 出去
```

4. **异常类型不匹配**——抛受检异常但没配 `rollbackFor`（默认只回滚 RuntimeException/Error）
5. **类没交给 Spring 管理**——没加 `@Service`，压根没有代理
6. **数据库引擎不支持事务**——表是 MyISAM（InnoDB 才支持事务），见 [[web后端开发/数据库/MySql/存储引擎|存储引擎]]
7. **多线程**——事务绑定在当前线程的数据库连接上，方法里开新线程执行的 SQL 不归这个事务管

排查顺序：是不是 Spring 管的 Bean → 方法是不是 public → 是不是 this 自调用 → 异常有没有真的抛到代理那层。

## 五、编程式事务（了解）

不想用注解、需要精细控制片段时：

```java
@Service
@RequiredArgsConstructor
public class DemoService {
    private final TransactionTemplate transactionTemplate;

    public void biz() {
        transactionTemplate.execute(status -> {
            // 这一段在事务里
            return null;
        });
        // 这一段不在
    }
}
```

日常开发 99% 用声明式，知道有这个东西即可。
