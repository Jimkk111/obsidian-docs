## 一、为什么要统一处理

Service 里随便一抛，浏览器拿到的是 Spring 默认的 500 白页/默认 JSON：

```json
{ "timestamp": 1760000000000, "status": 500, "error": "Internal Server Error", "path": "/users" }
```

前端没法据此给出友好提示，后端也丢了上下文。目标：**任何异常，最终都变成统一的 `Result` 结构返回**：

```json
{ "code": 5001, "message": "用户名已存在", "data": null }
```

## 二、@RestControllerAdvice 全局兜底

```java
@RestControllerAdvice                 // 对所有 Controller 生效的增强（= @ControllerAdvice + @ResponseBody）
@Slf4j
public class GlobalExceptionHandler {

    // 优先匹配：越具体的异常类型越优先
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusiness(BusinessException e) {
        log.warn("业务异常: {}", e.getMessage());          // 业务异常是预期内的，warn 即可
        return Result.error(e.getCode(), e.getMessage());
    }

    // 参数校验失败（@Valid 场景）
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().get(0).getDefaultMessage();
        return Result.error(400, msg);                     // 只提示第一条校验错误
    }

    // 兜底：所有没被上面接住的异常
    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e) {
        log.error("未知异常", e);                          // 必须带堆栈，否则线上无从排查
        return Result.error(500, "服务器开小差了，请稍后再试");  // 不把内部细节暴露给前端
    }
}
```

规则：`@ExceptionHandler(XX.class)` 接住 XX 及其子类；多个 handler 时**按异常类型继承关系取最具体的那个**。

## 三、自定义业务异常

预期内的失败（用户名重复、余额不足）不该用 `RuntimeException("xxx")` 裸抛，定义专门的类型：

```java
@Getter
public class BusinessException extends RuntimeException {    // 继承 RuntimeException → 抛出不用 declare
    private final Integer code;

    public BusinessException(Integer code, String message) {
        super(message);
        this.code = code;
    }
}
```

Service 里正常写业务，失败就抛：

```java
public void register(User user) {
    if (userMapper.countByName(user.getName()) > 0) {
        throw new BusinessException(5001, "用户名已存在");   // 抛出去，全局处理器接住
    }
    userMapper.insert(user);
}
```

链路：`Service throw` → 冒泡出 Controller → `@RestControllerAdvice` 匹配 handler → 组装 `Result` 返回前端。**Controller 里从此不用写 try-catch**。

配合事务注意：异常抛出后 `@Transactional` 才会回滚——所以"抛业务异常"和"事务回滚"是天然联动的；但 try-catch 吞掉异常会导致不回滚，见 [[web后端开发/JavaWeb/springboot/spring/事务管理|事务管理]] 失效场景。

## 四、错误码约定（简单实践）

| 区间 | 含义 |
|---|---|
| 0 / 200 | 成功 |
| 400~499 | 客户端问题：参数错误、未登录（401）、无权限（403） |
| 500~599 | 服务端问题：5000 未知、5001 起按业务分配（5001 用户名已存在…） |

## ⚠️ 常见坑

1. **兜底 handler 不打日志** → 线上只看到"服务器开小差"，日志里什么都没有，没法排查；必须 `log.error("...", e)` 带堆栈
2. **把堆栈直接返回给前端** → 泄露内部实现（类名、SQL），给攻击者送信息；对外只回友好文案
3. **全局异常处理管不到的地方**：它只接 Controller 调用链上的异常（含拦截器、参数绑定）；自己在方法里 `try-catch` 吞掉的、定时任务线程里的、异步线程里的异常，它都接不住
4. **异常处理类没被扫描到** → 放在启动类所在包及子包下（和其他 @Component 同规则）
